## 通用约定

### 认证方式
- 除登录/健康检查外，所有接口需携带请求头：
  ```
  Authorization: Bearer {token}
  ```
- Token 有效期 24 小时（`Jwt:ExpireMinutes`，默认 1440，可配 5~1440），通过 `POST /auth/login` 获取；前端 15 分钟无操作自动退出登录。
- Token 内含 `password_version` claim，**改密码后旧 Token 全部失效**。

### 响应统一格式
所有接口返回统一信封：

```json
{
  "success": true,
  "message": "操作成功",
  "data": { },
  "errorCode": null
}
```

| 字段 | 说明 |
|------|------|
| `success` | 是否成功 |
| `message` | 提示信息 |
| `data` | 业务数据 |
| `errorCode` | 业务错误码（成功为 null） |

### HTTP 状态码
| 码 | 含义 |
|----|------|
| 200 | 成功 |
| 400 | 参数错误（业务异常） |
| 401 | 未登录 / Token 失效 / 认证失败（登录或密码重置时用户名或密码/验证信息错误，含防枚举的统一提示） |
| 403 | 无权限 |
| 404 | 资源不存在 |
| 429 | 操作过于频繁（登录 1 分钟 5 次 / 密码重置 15 分钟 3 次） |

### 角色说明
| 角色 | 简称 | 权限 |
|------|------|------|
| SYSTEM_ADMIN | 系统管理员 | 全部 |
| STORE_MANAGER | 门店经理/店长 | 管理端（排班规则只读） |
| EMPLOYEE | 员工 | 员工端 |
| 兼职（is_parttime=1） | 兼职员工 | 员工端 + 仅低技能岗位排班 |

## 认证接口

### 1.1 登录
`POST /auth/login`

请求：
```json
{ "username": "admin", "password": "Admin@123456" }
```

响应 data：
```json
{
  "token": "eyJhbGciOiJIUzI1NiIs...",
  "expiresAt": "2026-08-19T17:00:00Z",
  "user": { "id": 1, "storeId": 1, "username": "admin", "nickname": "系统管理员", "role": "SYSTEM_ADMIN", "passwordVersion": 1 }
}
```

限流：1 分钟 5 次（按账号 + IP 双维度计数，登录成功同时清除该 IP 与账号的失败计数/锁定）。

### 1.2 ~~发送密码重置验证码~~（已下线）

`POST /auth/send-reset-otp` 已于 2026-08-21 移除：忘记密码流程改为**用户名 + 注册手机号直接重置（无验证码）**，见 1.3。OTP 生成/校验代码（`PasswordResetService.GenerateOtp/ValidateOtp`）为遗留死代码，未接入任何端点。

### 1.3 忘记密码（重置）
`POST /auth/forgot-password`

请求：
```json
{
  "username": "E001",
  "verifyInfo": "13800000001",
  "otpCode": "123456",
  "newPassword": "NewPass123",
  "confirmPassword": "NewPass123"
}
```

> 新密码 ≥8 位且含大写/小写/数字；bcrypt work factor 12 存储；重置成功后该用户 `password_version` +1，旧 Token 全部失效。

### 1.4 获取当前用户
`GET /auth/me`

响应 data：`{ "id": 1, "storeId": 1, "username": "admin", "nickname": "系统管理员", "role": "SYSTEM_ADMIN", "passwordVersion": 1 }`

## 高峰禁休时段

> 班中休息（30 分钟固定休息）**不得与高峰时段重叠**；无任何启用配置时算法兜底默认 20:00-22:00。

### 8.1 高峰时段列表
`GET /peak-restricted-hours`（AdminOnly）

响应 data：
```json
[{ "id": 1, "startTime": "20:00:00", "endTime": "22:00:00", "status": 1 }]
```

### 8.2 新增高峰时段
`POST /peak-restricted-hours`（AdminOnly）

请求：`{ "startTime": "20:00", "endTime": "22:00", "status": 1 }`

校验：HH:mm 格式、**30 分钟对齐**、开始早于结束、启用区间不得与已有配置重叠、启用状态最多 10 条。错误码：`INVALID_PEAK_HOUR` / `PEAK_HOUR_OVERLAP` / `TOO_MANY_PEAK_HOURS`。

### 8.3 修改高峰时段
`PUT /peak-restricted-hours/{id}`（AdminOnly）

请求同 8.2（可同时改启停状态）。

### 8.4 删除高峰时段
`DELETE /peak-restricted-hours/{id}`（AdminOnly）

> 增删改均写审计日志（`CREATE_PEAK_HOUR` / `UPDATE_PEAK_HOUR` / `DELETE_PEAK_HOUR`）。

## 人数需求

> 人数需求 = 日期类型（WORKDAY/WEEKEND/HOLIDAY）× 工作站 × 30 分钟时段。
> 营业日口径：**当天 12:00 至次日 06:00**（06:00-11:30 闭店时段隐藏但数据保留）；
> 凌晨时段（00:00-05:30）按**前一天**的日期类型取需求（跨天班次口径）。

### 9.1 查询人数需求
`GET /staffing-requirements?dayType=WORKDAY`（AdminOnly）

响应 data（数组）：
```json
[{
  "id": 1, "dayType": "WORKDAY", "workstationId": 10, "workstationCode": "SERVICE",
  "workstationName": "服务岗", "timeSlot": "19:00:00",
  "requiredCount": 2, "idealCount": 3, "remark": "周末加档"
}]
```

- `requiredCount`：最少人数（硬性，低于即缺口，影响发布与合理度）
- `idealCount`：最好人数（软性，人手有余时尽量补足；`idealCount >= requiredCount`）

### 9.2 批量保存人数需求
`PUT /staffing-requirements`（AdminOnly）

请求：
```json
{
  "dayType": "WORKDAY",
  "entries": [
    { "workstationId": 10, "timeSlot": "19:00", "requiredCount": 2, "idealCount": 3, "remark": "周末加档" }
  ]
}
```

- `timeSlot` 格式 HH:mm 或 HH:mm:ss，必须 30 分钟对齐；
- `idealCount` 缺省为 0 时视为与 `requiredCount` 相同；未提交的工作站时段视为 0；
- `remark` 最长 200 字符，空白转 NULL。

响应 data：`{ "dayType": "WORKDAY", "totalSlots": 210, "nonZeroSlots": 86 }`

### 9.3 周期需求预览
`GET /staffing-requirements/preview?startDate=2026-09-01&endDate=2026-09-30`（AdminOnly）

按营业日口径统计所选周期各日期类型的天数/最少与最好需求人·时/峰值并发人数及出现时段（生成排班页的周期需求概览数据源）。

## AI 文档识别

> 基于 DeepSeek `/chat/completions`（`response_format=json_object`，temperature=0）识别 Excel/图片中的人数需求；
> 结果逐条校验（日期类型/工作站匹配/30 分钟对齐/人数范围），识别结果需在人数需求页点「保存」才写库。

### 10.1 获取 AI 配置
`GET /ai/config`（AdminOnly）

响应 data：`{ "configured": true, "provider": "DeepSeek", "baseUrl": "https://api.deepseek.com", "model": "deepseek-chat", "maskedKey": "sk-****abcd" }`

> API Key 明文存库（按门店），**接口只返回掩码**。

### 10.2 保存 AI 配置
`PUT /ai/config`（AdminOnly）

请求：`{ "apiKey": "sk-...", "baseUrl": "https://api.deepseek.com", "model": "deepseek-chat" }`

> `apiKey` 留空表示保持现有 Key 不变。

### 10.3 AI 连通性测试
`POST /ai/test`（AdminOnly）

响应 data：`{ "success": true, "message": "连接成功" }`（前端超时 130 秒）

### 10.4 AI 识别人数需求文档
`POST /ai/parse-requirement-doc`（AdminOnly）

请求（`kind=sheet` 表格文本）：
```json
{
  "kind": "sheet", "fileName": "9月需求.xlsx",
  "rows": [["服务岗", "19:00", "2"], ["保洁岗", "21:00", "1"]]
}
```

请求（`kind=image` 图片）：`{ "kind": "image", "fileName": "photo.png", "imageBase64": "...", "imageMimeType": "image/png" }`

响应 data：
```json
{
  "parsed": 8, "skipped": 1,
  "entries": [{ "dayType": "WORKDAY", "workstationId": 10, "timeSlot": "19:00", "requiredCount": 2, "idealCount": 2 }],
  "warnings": ["跳过：无法匹配工作站「未知岗」"]
}
```

> 注意：deepseek-chat 不支持图片输入时，`kind=image` 会返回 400，前端页面会给出明确提示。

## 排班计划

### 12.1 一键生成排班
`POST /schedules/generate`（AdminOnly）

请求：
```json
{ "startDate": "2026-09-01", "endDate": "2026-09-30", "planName": "9月排班" }
```

响应 data：
```json
{
  "planId": 30, "planName": "9月排班",
  "restDayCount": 132, "shiftAssignmentCount": 700,
  "workstationAssignmentCount": 2400, "summaryCount": 960, "issueCount": 15,
  "issueTypes": ["STAFFING_GAP", "OVERTIME"],
  "demandMinHours": 4200, "demandIdealHours": 4680,
  "coveredHours": 4050, "gapHours": 150, "coveragePct": 96,
  "demandShiftCount": 34
}
```

- 四阶段引擎：休息日 → 班次（全职优先；模板班次不足时按连续缺口块**自动生成临时班次 D1/D2…**）→ 工作站 → 班中休息（30 分钟固定休息，与高峰禁休时段不重叠）。
- `demandMinHours/demandIdealHours`：周期最少/最好需求人·时；`coveredHours/gapHours/coveragePct`：已覆盖/缺口人·时与覆盖率（**按最少人数口径**）；`demandShiftCount`：临时补班班次数。

> 同周期已有 DRAFT 计划时自动覆盖并重新生成；已有 PUBLISHED 则拒绝。

### 12.2 排班计划列表
`GET /schedules?page=1&pageSize=20&status=`（AdminOnly）

响应 data：
```json
{
  "items": [{ "id": 30, "planName": "9月排班", "startDate": "2026-09-01", "endDate": "2026-09-30", "status": "DRAFT", "createdBy": 1, "publishedAt": null, "createdAt": "...", "employeeCount": 30, "issueCount": 15 }],
  "page": 1, "pageSize": 20, "total": 5
}
```

### 12.3 删除排班计划
`DELETE /schedules/{planId}`（AdminOnly）级联删除明细/汇总/问题/换班。

### 12.3b 取消发布
`POST /schedules/{planId}/unpublish`（AdminOnly）：已发布计划退回草稿（PublishedAt 清空、明细回 DRAFT），并通知员工「排班已取消」。仅 PUBLISHED 状态可调用，草稿调用返回 400 `NOT_PUBLISHED`。

### 12.3c 空位加人（P3）
- `GET /schedules/{planId}/add-candidates?workDate=&timeSlot=&workstationId=`（AdminOnly）：候选员工列表（具备工作站技能、当天未排班、无已批准请假；兼职仅限低技能岗位；当天休息的员工带 `isRestDay=1` 标记）。
- `PUT /schedules/{planId}/add-slot`（AdminOnly）：给员工新增连续 30 分钟上班段（不挂班次模板），草稿与已发布计划均允许；已发布时自动通知该员工「排班变更」（含时段范围与段数）。
- 请求：`{ "employeeId": 15, "workDate": "2026-09-03", "timeSlots": ["20:00:00", "20:30:00"], "workstationId": 10 }`
- 校验：30 分钟对齐、时段必须连续（时间轴 13:00 起，跨午夜 00:00~05:30 属当天末尾，400 `INVALID_TIME_SLOT`）、单次最多 68 段、技能、兼职低技能岗位限制、当天已批准请假（400 `ON_LEAVE`）、同员工所选时段重复（400 `SLOT_ALREADY_ASSIGNED`）。汇总按当天全部时段重算起止/工时（0.5h/段）与覆盖工作站。

### 12.4 手动调整排班
`PUT /schedules/{planId}/adjust`（AdminOnly）

请求：
```json
{
  "items": [
    { "employeeId": 15, "workDate": "2026-09-03", "timeSlot": "19:00:00", "shiftTemplateId": 4, "workstationId": 10 }
  ]
}
```

配套细分端点（日明细甘特图拖动/点击操作）：
- `PUT /schedules/{planId}/day-status`：批量设置员工某天休息/上班状态（`items: [{ employeeId, workDate, isRestDay, shiftTemplateId?, workstationId? }]`）
- `PUT /schedules/{planId}/slot-status`：批量设置员工某天某个半小时时段为休息/恢复上班（`items: [{ employeeId, workDate, timeSlot, isRest }]`）
- `PUT /schedules/{planId}/move-segment`：移动员工某天工作段（换工作站/平移时间，吸附 30 分钟）

### 12.5 发布排班
`POST /schedules/{planId}/publish?force=false`（AdminOnly）

- 存在 ERROR 严重问题时若 `force=false` 返回 400（HAS_ERROR_ISSUES）
- 传 `force=true` 跳过障碍强制发布

## 对接注意事项

1. **认证**：所有业务接口需 `Authorization: Bearer {token}`，Token 24 小时过期（可配），改密码后旧 Token 立即失效。
2. **按门店隔离**：接口自动按当前登录用户所属门店过滤数据。
3. **权限分级**：
   - 排班规则修改 = **仅系统管理员**
   - 管理端接口 = 系统管理员 + 门店经理（高峰时段/人数需求/AI/技能矩阵/通岗管理员与店长均可）
   - 员工端 = 登录员工本人
4. **排班问题类型**：对接方可按 `issueType` 分类处理（缺口/技能/工时/连续工作/休息顶岗）。
5. **兼职数据**：员工 `isParttime=1` 时仅具备低技能岗位技能（保洁/咨客/传送/服务），可作为外部排班系统的兼职资源。
6. **人数需求口径**：营业日 = 当天 12:00 至次日 06:00；凌晨时段按前一天日期类型取需求；需求分最少（硬性）/最好（软性）两档。
7. **敏感数据**：员工手机号已脱敏；AI API Key 只回传掩码；密码重置验证码不进响应体。
