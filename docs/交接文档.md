## 1. 项目概况

- **名称**：排班系统 MVP（案例门店：昆明滚滚）
- **形态**：管理端 Web 单页应用 + 员工自助端（同一前端按角色路由分流）
- **技术栈**
  - 后端：.NET 10.0 Web API（Minimal API，集中在 `Program.cs`，共 **66 个端点**）+ EF Core + Pomelo MySQL
  - 数据库：MySQL（`shift_mvp` 库）
  - 前端：Vue 3 + Element Plus + Vite 6 + Pinia + Vue Router + ECharts + axios + dayjs
  - 认证：JWT Bearer（令牌有效期 24 小时）+ 角色授权策略（`AdminOnly` / `SystemAdminOnly`）；前端 15 分钟无操作自动退出登录（`stores/auth.js` 空闲监听）
  - 测试：xUnit，当前 **186 个用例全部通过**（2026-08-19 实测 ~5s；覆盖算法/应用服务/安全/异常中间件/基础设施，测试数据层用 EF Core InMemory + SQLite）
- **人员规模**：33 名员工（23 全职 + 10 兼职 E101~E110），25 个登录账号（admin + E001/manager + E002~E023）；**兼职 E101~E110 无登录账号**（仅排班数据）
- **文档现状**：
  - `README.md` / `docs/功能清单.md` / `docs/接口文档.md`（已升 **v1.1**）—— 均随本轮同步至 2026-08-19 状态
  - 新增测试类文档：`docs/测试计划.md`（手工测试计划 MTP-2026-08）、`docs/测试报告.md`（单元测试报告）、`docs/集成测试报告.md`（API 级端到端）、`docs/代码审查报告-2026-08-18.md`

### 20260818 迁移内容（人数需求三档化）

1. 日期类型三档化：`date_parameters.day_type` 支持 **WORKDAY / WEEKEND / HOLIDAY**。业务口径：平日 = 周一~周四+周日，**周末 = 周五+周六（晚市高峰日）**，节假日 = 法定节假日（2026-09-25/26 中秋）。
2. 重新划分历史日期：周五/周六改判 `WEEKEND`，周日改判 `WORKDAY`，中秋 09-25/26 标记 `is_legal_holiday=1`、09-27 调休补班。
3. 为每个门店复制 HOLIDAY 人数需求作为 `WEEKEND` 初始值（幂等，可重复执行）。
4. 配套新功能：管理端「基础数据 → 人数需求」页面（矩阵编辑 + Excel 导入/模板导出 + 跨日期类型复制），后端 `GET/PUT /api/staffing-requirements`。

### 20260819 迁移内容（人数需求两档化）

1. `staffing_requirements` 新增 `ideal_count`（最好人数）列，并回填 = `required_count`（最少人数）。
2. 语义：单元格单数字 N = 最少且最好 N；`(M,N)`（页面与 Excel 均支持） = 最少 M、最好 N。
3. 排班算法：硬性满足最少人数（低于即缺口），人手有余时通过软性阶段尽量补足最好人数（`ShiftAllocator` 两阶段填充 + `WorkstationAllocator` 2A+ 软性参考分配），软性缺口不影响发布与合理度（合理度仍按最少人数计算）。
4. 前端页面改为甘特图式编辑：行=工作站、列=半小时时段，**时间轴为营业时段 12:00 至次日 06:00**（00:00 起标注「次日」，06:00-11:30 闭店时段隐藏但数据保留），颜色深浅=最少人数、斜纹=有最好目标；点击单元格编辑，按住拖动框选区域后弹出批量修改面板（最少/最好 + 快捷键，应用到选区）。
5. 营业日口径（20260819 追加）：**一个营业日 = 当天 12:00 至次日 06:00**；排班算法中，某日历日 00:00-05:30 的凌晨时段按**前一天**的日期类型取人数需求（如周日 02:00 按周六=周末档），合理度计算同步按此口径。
6. 需求统计与按需排班（20260819 追加）：
   - 人数需求页实时统计每档的最少/最好人·时、峰值并发（含三档合计）；
   - 生成排班页展示周期需求概览（`GET /api/staffing-requirements/preview`）；
   - 排班引擎：模板班次排完后仍有最少人数缺口时，按连续缺口块自动生成**临时班次 D1/D2…**（起止时间跟随需求、可跨午夜，落库 `shift_template_id=NULL`，月/周视图显示班次代码「班」），生成结果返回需求/覆盖/缺口人·时与覆盖率（`GenerateScheduleResult` 新增 6 个字段）。

### 20260819_fix_workday_staffing 迁移内容（★ 本次新增）

1. 背景：旧版 init 仅配置 HOLIDAY（含周末）需求；20260818 拆分 WEEKEND 时只复制了 HOLIDAY→WEEKEND，导致 WORKDAY（周一~周四+周日）全 0、按需排班时无岗位安排。
2. 内容：按 init 业务口径无条件重算 WORKDAY 全部时段（行政岗 13:00-22:00=1；厨房 18:00-23:30=2、00:00-03:00=1；服务/传送 19:00-23:30=2、00:00-04:00=1；咨客/客户经理 19:00-23:30=1；内/外吧 18:30-23:30=1、00:00-04:00=1；保洁 21:00-23:30 或 00:00-06:00=1；其余时段 0），`required_count` 与 `ideal_count` 同步回填。
3. 幂等：UPDATE 无条件按口径重算，重复执行结果一致；审计日志按 action_type+remark 去重。

### 20260825 迁移内容（★ 店长工作站，本轮新增）

## 6. 后端架构与排班引擎

### 6.1 分层

- **端点层**：Minimal API 全部写在 `Program.cs`（66 个端点），统一 `ApiResponse` 信封、全局异常中间件、JWT 认证、按端点限流（登录 20 次/分、重置 15 分钟 3 次）。
- **应用层**：`Application/<领域>/` 下 `IXxxService` + `XxxService` + `XxxDtos`，业务事务内写审计日志（`IAuditLogService`，与业务同事务）。
- **算法层**：`Algorithm/` 纯 C# 类，输入/输出为 record（`SchedulingModels.cs`），不依赖 EF，可用内存数据单测。
- **持久层**：`ShiftSchedulingDbContext` + `Entities/`（snake_case 列映射）。

### 6.2 排班引擎四阶段（`SchedulingEngine.GenerateAsync`）

| 阶段 | 组件 | 职责 |
|---|---|---|
| 1 | `RestDayAllocator` | 休息日分配（月休按周期折算，连续工作达上限强制打断） |
| 2 | `ShiftAllocator` | 班次分配（全职优先，请假过滤；最少人数硬性填充 + 最好人数软性填充两阶段，模板班次不足时按连续缺口块自动生成临时班次 D1/D2…） |
| 3 | `WorkstationAllocator` | 工作站分配（2A-2G + 2A+ 软性参考：缺口块检测/块状借调/二次填补/逐段兜底，每人每天借调上限 2 次；兼职仅低技能岗位） |
| 4 ★ | `BreakAllocator` | **班中休息分配（本次新增）** |
| 4.5 ★ | `ResidualGapFiller` | **剩余缺口兜底填充（本轮修复）：全职优先接整块（≥每日最低工时），兼职接碎片块；缺口块与员工已有班次部分重叠时按最长可接连续子段裁剪补班（原整块拒绝致缺口虚高）** |

> **S10 店长班优先级**：`ShiftAllocator.ShiftPriorityMap` 硬编码 `S10=1`（先于 S1 等行政班分配，保证店长休息日副手先被店长班占用）；**前端班次管理页 S10 的「优先级」输入已禁用**（界面修改不生效）。map 未收录的班次按 `int.MaxValue` 排最后，仅改模板 priority 无效。

### 6.3 ★ 班中休息规则（阶段四，`BreakAllocator.cs`）

- 每次休息固定 **30 分钟**；班次时长 **< 4 小时不安排休息**；上班 2 小时内、下班 1 小时内禁休。
- **休息不得与高峰禁休时段重叠**（无配置时算法兜底默认 20:00-22:00）。
- 选槽优先级：休息后本岗冗余最大 → 离高峰边界越远越好 → 该槽休息人数最少（分散休息）。
- 冗余不足时**借调顶岗**：候选人需当班覆盖该时段 + 有该站技能 + 该时段原分配在其他站 + 离开原岗位后原站不缺人；主技能优先、技能分高者优先；**每人每天最多借调 2 次**。
- 不熟练借调输出 `BREAK_BORROW_INEXPERIENCED`（INFO）；无人顶岗输出 `BREAK_UNCOVERED`（WARN，店长人工处理）；高峰把整个可休窗口挤没时休息被迫安排在窗口起点并告警。
- **休息照算工时**（不扣减 WorkHours）。跨午夜班次结束时间按 24 小时制回绕。

### 6.4 ★ 高峰禁休时段（`PeakHours/`）

- 每门店可配置多条（启用状态上限 **10 条**），时间 **30 分钟对齐**、开始早于结束、启用区间不可重叠。
- 接口：`GET/POST/PUT/DELETE /api/peak-restricted-hours`（`AdminOnly`），增删改全部写审计日志。
- 前端管理页 `/peak-hours`（`PeakHoursView.vue`），菜单项「高峰时段」。

### 6.5 合理度（rationality）

- `/schedules/{planId}/rationality`：按真实覆盖 ÷ 需求计算（最少人数口径）；**无人顶岗的班中休息时段覆盖人数 -1**（有借调顶岗的不扣减），支持跨午夜回绕判断。
- 08-19 修复后合理度由 87% 提升至 97%：D 班次按岗位分块、借调防拆墙、支持不重叠补班（`5a56605`）。

### 6.6 AI 文档识别（`Application/Ai/`）

- `AiConfigService`：按门店保存 DeepSeek 配置（API Key 明文存库、接口仅返回掩码）；`DocumentAiService`：调用 DeepSeek `/chat/completions`（json_object、temperature=0），支持表格文本与图片 base64 输入，结果逐条校验（日期类型/工作站匹配/30 分钟对齐/人数范围）。
- 端点（AdminOnly）：`GET/PUT /api/ai/config`、`POST /api/ai/test`（连通性）、`POST /api/ai/parse-requirement-doc`（识别）。
- 注意：deepseek-chat 不支持图片输入，`kind=image` 会返回 400，前端页面有明确提示。

## 11. 已知问题与注意事项

- **BREAK_UNCOVERED 告警需人工**：高峰禁休、短班、借调不满足时算法只告警不强制解决，发布前店长需处理（发布页问题列表可见）。

- **借调上限**：工作站借调与休息顶岗各自独立限制每人每天 2 次。
- **MySQL 版本**：代码声明 ServerVersion 8.0.36，本机 MySQL 9.6 实测正常；如遇 Pomelo 兼容问题，优先对齐 8.0。
- **`Program.cs` 是单文件 1800+ 行**：改端点建议按既有分区注释定位；后续可考虑迁移到控制器或按领域拆分，但当前勿做无谓重构。

- **`database/backups/` 含历史明文密码备份**（`shift_mvp_before_init_20260806_154731.sql` 中可见 `admin123_dev_plaintext_replace_later`），已被 .gitignore 排除，勿提交、勿外传。
- **AI 图片识别**：deepseek-chat 不支持图片输入，`kind=image` 会返回 400；换用支持视觉的模型后 `DocumentAiService` 无需改动。
