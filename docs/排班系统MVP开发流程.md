# 排班系统 MVP 开发流程

> 项目名称：排班系统 MVP  
> 案例门店：昆明滚滚  
> 开发范围：管理端 + 后端 API + 排班算法 + MySQL 数据库 + 站内模拟通知  
> 暂不开发：员工 H5 端、真实短信通知、复杂审批流、复杂成本分析、多门店分片部署  
> 后端技术：.NET 6.0 或以上，MVP 阶段优先按 .NET 6.0 兼容设计  
> 前端技术：Vue 3 + Element Plus  
> 数据库：MySQL 5.7  
> 本机数据库：`shift_mvp`  
> MySQL 密码：由本地配置读取，当前开发环境为 `root123`  
> 通知方式：站内模拟通知  

---

## 1. 总体开发目标

本 MVP 的目标不是一次性完成完整企业级排班平台，而是先交付一个可以演示、可以运行、可以验证核心算法和业务闭环的管理端系统。

MVP 完成后，应支持以下完整流程：

1. 管理员登录系统；
2. 查看昆明滚滚门店基础数据；
3. 维护员工、岗位、工作站、班次、技能、规则；
4. 选择排班周期，一键生成排班；
5. 系统执行休息日分配、班次分配、工作站分配；
6. 管理员查看周排班、月排班、日排班明细；
7. 系统展示冲突、缺口和合规检查结果；
8. 管理员可以手动调整排班；
9. 调整操作写入审计日志；
10. 管理员发布排班；
11. 系统生成站内通知；
12. 管理员查看工时统计、合规报告、审计日志和通知记录。

## 2. 已确认约束

### 2.1 技术约束

| 项目 | 约束 |
|---|---|
| 后端 | .NET 最低 6.0 |
| 前端 | Vue 3 + Element Plus |
| 数据库 | MySQL 5.7 |
| 缓存 | MVP 可预留 Redis 接口，非核心流程可先不强依赖 |
| 通知 | 站内模拟通知 |
| 客户端范围 | 只做管理端 |
| 数据范围 | 先按昆明滚滚模拟数据 |
| 交付目标 | MVP，可运行、可演示、可迭代 |

### 2.2 业务约束

MVP 阶段重点实现以下业务规则：

1. 每名员工默认每月休息 4 天；
2. 每名员工只能安排到具备技能的班次或工作站；
3. 内吧岗和外吧岗技能互通；
4. 按 S1-S8 班次模型进行排班；
5. 按 13 个工作站进行岗位覆盖；
6. 每半小时作为一个排班时间槽；
7. 尽量满足每工作站每半小时的最低人数需求；
8. 尽量减少员工同一天内频繁切换工作站；
9. 生成无法满足的缺口报告；
10. 手动调整必须记录审计日志。

## 4. 后端开发流程

### 4.1 后端总体架构

后端采用分层结构，保证业务逻辑、排班算法、数据库访问和接口层解耦。

建议后端逻辑分层如下：

| 层级 | 作用 |
|---|---|
| API 层 | 提供 HTTP 接口，处理请求、认证、参数校验、统一响应 |
| Application 应用层 | 编排业务流程，例如一键排班、发布排班、手动调整 |
| Domain 领域层 | 定义核心业务对象、规则、算法模型 |
| Algorithm 算法层 | 实现休息日分配、班次分配、工作站连续性分配 |
| Infrastructure 基础设施层 | 数据库访问、配置读取、日志、站内通知、审计记录 |

### 4.2 后端基础能力

#### 4.2.1 统一响应格式

所有接口统一返回结构，包含：

- 状态码；
- 消息；
- 数据；
- 错误详情，必要时返回。

这样前端可以统一处理成功、失败、登录过期、权限不足、业务校验失败等场景。

#### 4.2.2 全局异常处理

后端需要统一捕获异常并转为标准响应。

处理范围包括：

- 参数错误；
- 登录失效；
- 权限不足；
- 数据不存在；
- 排班规则违反；
- 数据库异常；
- 未知系统异常。

#### 4.2.3 JWT 登录认证

MVP 阶段先实现管理员登录。

需要支持：

- 用户名密码登录；
- 返回 token；
- 前端携带 token 访问接口；
- 后端识别当前用户；
- 登录过期后返回统一错误。

#### 4.2.4 简化权限模型

MVP 阶段只需要满足管理端使用。

建议角色：

| 角色 | 权限 |
|---|---|
| 系统管理员 | 拥有全部配置和管理权限 |
| 门店经理 | 拥有当前门店排班、员工、规则、报表权限 |

普通员工权限可暂缓，因为当前不做 H5 员工端。

#### 4.2.5 审计日志

所有关键操作需要记录：

- 操作人；
- 操作时间；
- 操作类型；
- 操作对象；
- 变更前内容；
- 变更后内容；
- 门店 ID。

MVP 中至少记录：

- 新增/修改员工；
- 修改班次；
- 修改规则；
- 一键生成排班；
- 手动调整排班；
- 发布排班。

## 5. 数据库开发流程

### 5.1 数据库设计原则

MySQL 5.7 下需要注意：

1. 字符集统一使用 utf8mb4；
2. JSON 字段只作为存储，不作为核心查询条件；
3. 技能匹配在后端内存中完成；
4. 不依赖 MySQL 8 的窗口函数、CTE 等能力；
5. 核心查询字段建立索引；
6. 业务数据尽量使用软删除或状态字段；
7. 涉及排班生成、发布、调整的操作要使用事务；
8. 深分页报表优先使用游标方式。

## 7. 排班算法开发流程

### 7.1 算法设计目标

MVP 算法目标是：

1. 能稳定生成排班；
2. 能解释为什么这样排；
3. 能输出缺口和违规；
4. 能让管理员手动调整；
5. 后续可以继续优化。

MVP 阶段不追求数学最优解，而是采用规则驱动 + 贪心策略 + 连续性优化。

### 7.2 算法输入模型

算法输入包括：

- 员工列表；
- 员工技能矩阵；
- 员工部门；
- 员工偏好；
- 员工不可用时段；
- 日期参数；
- 班次模板；
- 排班需求矩阵；
- 规则配置。

### 7.3 算法输出模型

算法输出包括：

- 员工休息日；
- 员工每日班次；
- 员工每半小时工作站；
- 日汇总；
- 工时统计；
- 岗位缺口；
- 规则违规报告。

### 7.4 阶段一：休息日分配

#### 要做什么

给每位员工在排班周期内分配休息日。

#### 怎么做

1. 读取规则配置中的默认休息天数；
2. 将日期分为平日、周末、节假日、节假日前夜；
3. 将员工按部门分类；
4. 行政员工优先从周末中选择休息日；
5. 服务员工优先从平日中选择休息日；
6. 服务员工尽量避开节假日前夜休息；
7. 每轮为未满足休息天数的员工分配一天；
8. 分配时优先选择当天休息人数较少的日期；
9. 最终校验每人休息天数是否正确；
10. 如果不足则补齐，如果超出则回滚或调整。

#### 输出

- 每位员工的休息日列表。

#### 验收标准

- 每位员工休息天数符合规则；
- 每天休息人数相对均衡；
- 服务员工尽量避开关键营业日休息。

### 7.5 阶段二：班次分配

#### 要做什么

为非休息员工分配 S1-S8 班次。

#### 怎么做

1. 对每一天获取上班员工；
2. 计算每个班次对应工作站的预估需求；
3. 判断员工是否具备该班次资格；
4. 资格判断依据是员工在班次覆盖工作站中至少有一个技能分大于 0；
5. 特殊处理内吧岗和外吧岗技能互通；
6. 按稀缺班次优先级分配；
7. 稀缺班次顺序为 S7、S8、S2、S3、S1、S6、S4、S5；
8. 对候选员工按技能覆盖广度、技能分、当前累计工时排序；
9. 优先分配技能覆盖广、技能分高、工时较低的人；
10. 剩余员工分配到需求缺口最大的班次；
11. 对无法分配班次的员工生成异常记录。

#### 输出

- 员工每日班次分配结果。

#### 验收标准

- 员工不会被分配到完全不具备技能的班次；
- 厨房、工程、吧台等稀缺岗位优先得到保障；
- 工时分布尽量均衡。

### 7.6 阶段三：连续性优先工作站分配

#### 要做什么

为每位员工在班次内的每半小时分配具体工作站。

#### 怎么做

##### 第一步：逐段参考分配

1. 遍历每一天；
2. 遍历每半小时槽位；
3. 获取当前在岗员工；
4. 获取当前槽位各工作站需求；
5. 按需求高低排序工作站；
6. 按技能分为员工分配工作站；
7. 生成一份不考虑连续性的参考分配。

##### 第二步：确定主工作站

1. 统计每位员工在参考分配中出现最多的工作站；
2. 如果出现次数相同，选择员工技能分更高的工作站；
3. 将其作为员工当天主工作站。

##### 第三步：初始连续分配

1. 将员工当天所有在岗时间先统一安排到主工作站；
2. 得到一个连续性最强的初始方案。

##### 第四步：检测缺口块

1. 对每个工作站扫描每半小时实际人数；
2. 与需求人数对比；
3. 如果实际人数少于需求人数，标记缺口；
4. 将连续缺口合并为缺口块；
5. 计算缺口严重程度。

##### 第五步：块状借调

1. 按缺口严重程度排序；
2. 查找整个缺口块都在岗的候选员工；
3. 候选员工必须具备目标工作站技能；
4. 候选员工从原工作站借出后，原工作站尽量不能产生新缺口；
5. 优先借调目标技能分高、当天借调次数少的人；
6. 整块切换，不做频繁交替。

##### 第六步：二次补缺

1. 重新扫描缺口；
2. 对残留缺口再次形成缺口块；
3. 放宽借出限制；
4. 尽量补齐关键工作站缺口。

##### 第七步：最终兜底

1. 对仍然无法满足的缺口逐时段处理；
2. 如果仍无法满足，则生成缺口报告；
3. 不强行制造明显不合理的排班。

#### 输出

- 每个员工每天每半小时的工作站分配；
- 缺口报告；
- 借调记录；
- 连续性统计。

#### 验收标准

- 员工工作站切换次数尽量少；
- 关键岗位缺口优先被补齐；
- 人力不足导致的缺口能够清晰报告；
- 不会隐藏无法满足的问题。

## 13. 开发风险与处理策略

### 13.1 算法无法满足所有岗位需求
原因：人员技能或人数不足。

处理：

- 不强行伪造满足结果；
- 输出清晰缺口报告；
- 标明缺口工作站、日期、时间段和缺口人数。

### 13.2 跨天班次容易计算错误
处理：

- 所有班次统一转换为半小时槽位；
- 跨天班次使用明确的日期归属规则；
- 日明细展示时区分工作日期和实际时间。

### 13.3 MySQL 5.7 JSON 查询能力有限
处理：

- 技能矩阵尽量单独建表；
- 不依赖 JSON 字段进行复杂查询；
- 算法所需数据一次性加载到内存。

### 13.4 前端排班视图复杂
处理：

- MVP 先用 Element Plus 表格实现；
- 周视图先保证可读和可调整；
- 后续再升级为甘特图或资源时间线。

### 13.5 手动调整影响复杂
处理：

- MVP 先做增量调整；
- 调整后重新校验相关日期；
- 对可能产生的缺口给出提示；
- 保留审计日志，方便回溯。
