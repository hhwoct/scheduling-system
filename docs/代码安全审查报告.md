# 排班系统代码安全与质量审查报告

> 审查日期：2026-08-10
> 审查范围：后端 .NET API（63 个 .cs 文件）、前端 Vue 3（30+ 个 .vue/.js 文件）、数据库 SQL（6 个文件）
> 审查重点：空指针（NPE）、SQL 注入、XSS、线程安全、参数校验、Mapper/SQL 配置错误、越权

---

## 一、总体结论

| 类别 | 风险等级 | 数量 |
|------|---------|------|
| 🔴 严重（必须修复） | 高 | 8 |
| 🟠 中等 | 中 | 10 |
| 🟡 轻微 | 低 | 6 |
| ✅ 良好实践 | - | 4 |

**最严重问题摘要**：
1. **垂直越权**：所有管理端接口仅 `RequireAuthorization()`，未限制角色，员工账号可直接调用管理接口
2. **水平越权**：`EmployeeService.QueryAsync`/`GetByIdAsync` 未按 `StoreId` 过滤，跨门店数据可读取
3. **事务一致性**：换班审批的数据交换与状态更新不在同一事务
4. **DTO 校验缺失**：多个请求模型无长度/格式/范围校验

## 二、严重问题（🔴 必须修复）

### 2.1 垂直越权：员工账号可调用所有管理接口
**位置**：`Program.cs`（全部管理端点）
**代码**：
```csharp
api.MapGet("/employees", ...).RequireAuthorization();          // 无角色限制
api.MapPost("/employees", ...).RequireAuthorization();          // 无角色限制
api.MapPut("/rules/{id:long}", ...).RequireAuthorization();     // 无角色限制
api.MapPost("/schedules/generate", ...).RequireAuthorization(); // 无角色限制
api.MapPut("/leave-requests/{id:long}/review", ...).RequireAuthorization(); // 仅拒绝 EMPLOYEE，但无 ADMIN 要求
```
**问题**：除少数接口（`/employee/*`、`/leave-requests/mine`、`/shift-swaps/mine`）有 `Role == "EMPLOYEE"` 判断外，所有管理接口仅校验"已登录"。**员工账号（ROLE=EMPLOYEE）可以直接调用**：
- `GET/POST/PUT/DELETE /api/employees`（员工管理）
- `PUT /api/rules/{id}`（规则配置）
- `POST /api/schedules/generate`、`PUT /api/schedules/{id}/adjust`（排班生成与调整）
- `PUT /api/leave-requests/{id}/review`（请假审批）
- `GET /api/audit-logs`（审计日志）
- `PUT /api/notifications/{id}/read`（通知管理）
- `PUT /api/leave-requests/{id}/review`（审批）

**修复建议**：为管理接口添加 `.RequireAuthorization("AdminOnly")` 策略，或在每个管理端点显式校验 `currentUser.Role != "EMPLOYEE"`。

### 2.2 水平越权：员工查询/详情未按门店过滤
**位置**：`EmployeeService.cs` 第 20-74 行
**代码**：
```csharp
public async Task<PagedResult<EmployeeListItem>> QueryAsync(EmployeeQueryRequest request, ...)
{
    var query = _dbContext.Employees
        .AsNoTracking()
        .Where(x => x.Status == (request.Status ?? 1));   // ← 无 StoreId 过滤！

public async Task<EmployeeDetail> GetByIdAsync(long id, ...)
{
    var employee = await _dbContext.Employees
        .AsNoTracking()
        .FirstOrDefaultAsync(x => x.Id == id, ...);       // ← 无 StoreId 过滤！
```
**问题**：`Program.cs` 第 209-211 行调用 `QueryAsync` 时**未传入 storeId**，`GetByIdAsync` 接口（第 216-223 行）也只传 id。任何门店的管理员可读取**所有门店**的员工列表与详情（姓名、电话、部门、周工时等敏感信息）。

**修复建议**：
```csharp
// QueryAsync 增加 storeId 参数
var query = _dbContext.Employees.Where(x => x.StoreId == storeId && x.Status == ...);
// GetByIdAsync 增加 storeId 参数
.FirstOrDefaultAsync(x => x.Id == id && x.StoreId == storeId, ...)
```

### 2.3 换班审批事务边界错误
**位置**：`Program.cs` 第 1203-1278 行（`PUT /api/shift-swaps/{id}/review`）
**代码**：
```csharp
await using var transaction = await db.Database.BeginTransactionAsync(ct);
// ... 交换 schedule_results、重建 schedule_summaries ...
await db.Database.CommitTransactionAsync(ct);   // ← 第 1249 行：事务提交

swap.Status = "APPROVED";                        // ← 第 1251 行：事务之后才改状态
swap.ReviewUserId = currentUser.UserId;
...
await db.SaveChangesAsync(ct);                   // ← 第 1263 行：另一事务保存状态
```
**问题**：
1. **数据与状态不一致**：若第 1263 行 `SaveChangesAsync` 失败（如网络中断），排班数据**已交换成功**但 `shift_swaps.status` 仍为 `PENDING`，用户可再次审批同一换班，造成数据重复交换。
2. `CommitTransactionAsync` 之后的异常不会被回滚。
3. **事务窗口缺失**：从「状态检查（第 1197 行 `swap.Status != "PENDING"`）」到「事务提交（第 1249 行）」之间无并发控制，两个管理员同时审批同一换班时，后一个会基于已被交换的数据再执行一次交换。

**修复建议**：
```csharp
// 1. 状态更新纳入同一事务
await using var transaction = await db.Database.BeginTransactionAsync(ct);
try
{
    // 先更新状态
    swap.Status = "APPROVED";
    swap.ReviewUserId = currentUser.UserId;
    ...
    // 再执行数据交换
    ...
    await db.SaveChangesAsync(ct);
    await db.Database.CommitTransactionAsync(ct);
}
catch { await db.Database.RollbackTransactionAsync(ct); throw; }
```
或对 `shift_swaps` 使用 `SELECT ... FOR UPDATE`（`db.ShiftSwaps.FromSqlRaw`）加行锁。

### 2.4 员工提交请假/审批缺少与排班联动校验
**位置**：`Program.cs` 第 824-983 行
**代码**：
```csharp
// 员工提交请假（824 行）
if (request.StartDate > request.EndDate) throw ...;  // 仅日期范围
// 无：请假日期与已发布排班冲突校验
// 无：重复请假校验（同一时间段多次提交）
// 无：请假时长上限校验（如连续 30 天）
```
```csharp
// 管理员审批（928 行）
if (review.Approved) leave.Status = "APPROVED";
// 无：批准后自动调整排班的逻辑（员工请假了但排班仍排他上班）
// 无：审批操作与排班生成的竞态控制
```
**问题**：
1. 员工可提交**与已发布排班冲突**的请假（如排班已安排上班的日期），审批通过后无联动调整，排班数据不真实。
2. 同一时间段可重复提交 N 个请假（无 `(employee_id, start_date, end_date)` 重叠检测）。
3. 审批通过后通知内容中拼接的 `leave.StartDate`/`leave.EndDate` 为用户可控日期，但格式化为 `yyyy-MM-dd`，风险可控。

**修复建议**：提交请假时检查已发布排班日期是否冲突；审批通过后自动生成或标记排班调整。

### 2.5 排班生成无幂等与并发保护
**位置**：`Program.cs` 第 418-433 行 + `ScheduleService.GenerateAsync`（27-157 行）
**代码**：
```csharp
api.MapPost("/schedules/generate", ...);  // 无并发控制
```
**问题**：
1. 无防重复提交：同一时间段可连续生成多个排班计划（无 `(store_id, start_date, end_date)` 唯一约束）。
2. 算法执行期间（`BuildInputAsync` + `Execute`）无数据库锁，若并发点击两次，两次读取的数据一致但生成两个计划，浪费资源。
3. 生成期间员工/技能/班次数据变化时（`BuildInputAsync` 与 `SaveChangesAsync` 之间），生成结果可能与实际不符。

**修复建议**：为 `schedule_plans` 增加 `(store_id, start_date, end_date)` 唯一索引；生成前先检查同周期已存在计划。

### 2.6 通知内容存储拼接用户可控输入（XSS 存储向量）
**位置**：`Program.cs` 多个端点
**代码**：
```csharp
// 发布排班通知（551 行）
Content = $"排班计划「{plan.PlanName}」已发布，请查看您的班表"
// plan.PlanName 来自用户输入（ScheduleService.cs 第 46 行 request.PlanName）

// 请假通知（867 行）
Content = $"{emp.Name}({emp.EmployeeNo}) 提交了 ... 的请假申请"
// emp.Name / emp.EmployeeNo 来自员工档案（用户输入）

// 换班通知（1068 行）
Content = $"{requesterEmp.Name}({requesterEmp.EmployeeNo}) 申请与 {targetEmp.Name}... 换班"
```
**问题**：员工姓名、工号、排班计划名等**用户可控输入**直接拼接进通知内容存入数据库。虽然当前前端使用 Vue 插值（默认转义，v-html 搜索为 0 处），但如果未来通知通过邮件/短信/Web 端未转义渲染，则构成**存储型 XSS 攻击向量**。特别是 `PlanName` 可以是任意 `<script>` 内容。

**修复建议**：
1. 后端对 `PlanName`、`Name`、`EmployeeNo` 等用户输入做 `System.Net.WebUtility.HtmlEncode` 或限制字符集（如姓名只允许中文/字母/·）。
2. 前端统一使用文本插值 `{{ }}`，禁止 `v-html`。

### 2.7 种子数据密码哈希硬编码且 admin/manager 相同
**位置**：`database/init_shift_mvp.sql` + `database/migrations/20260806_harden_user_passwords.sql`
**代码**：
```sql
INSERT INTO users (store_id, username, password_hash, nickname, role, status) VALUES
(1, 'admin', '$2y$12$ZBREG25aSw/EznOB14dL8Oj9kFOrFJSSVpmyrRm2q9qGAplc1mqC6', '系统管理员', 'SYSTEM_ADMIN', 1);
```
```sql
-- 20260806_harden_user_passwords.sql（"加固"迁移）
UPDATE users SET password_hash = '$2y$12$ZBREG25aSw/EznOB14dL8Oj9kFOrFJSSVpmyrRm2q9qGAplc1mqC6' WHERE username IN ('admin','manager');
```
**问题**：
1. 哈希硬编码在版本库中，属**已知明文哈希**（可离线破解）。
2. admin 与 manager **共享同一哈希** = 密码相同。
3. 迁移名为"加固"但哈希与 init 完全相同，**未实际更换密码**，是无效益的加固。

**修复建议**：删除 init SQL 中的明文哈希，改为**首次启动时由应用生成随机密码**并强制修改；或改用环境变量注入初始密码。

### 2.8 员工换班候选人接口缺少排班计划校验
**位置**：`Program.cs` 第 1109-1147 行
**代码**：
```csharp
// POST /api/shift-swaps/candidates
var summaries = await db.ScheduleSummaries.AsNoTracking()
    .Where(x => x.PlanId == req.PlanId && x.WorkDate == date && x.IsRestDay == 1 && x.EmployeeId != emp.Id)
    ...
```
**问题**：仅校验 `req.PlanId > 0` 和日期格式，**未校验该排班计划是否属于当前员工的门店且已发布**。员工可指定任意门店的 `planId` + 任意日期，读取其他门店的休息员工信息（员工号、姓名、部门），构成**跨门店信息泄露**。

**修复建议**：查询前先校验 `plan.StoreId == emp.StoreId && plan.Status == "PUBLISHED"`。

## 三、中等问题（🟠 建议修复）

### 3.1 管理端通知接口对 EMPLOYEE 角色存在数据泄露风险
**位置**：`Program.cs` 第 568-678 行
**问题**：`GET /api/notifications` 等接口接受任意登录用户，当 `Role == "EMPLOYEE"` 时通过 `EmployeeNo == Username` 关联员工；若用户名与工号不一致（如员工账号未配置），则返回空。但**管理端分支未限制角色**，员工伪造请求可获取门店下所有通知（含其他员工请假/换班信息）。

### 3.2 DbContext Fluent API 与数据库 DDL 不同步
**位置**：`ShiftSchedulingDbContext.cs`
**问题**：EF Core Fluent API 仅配置表名/列名/主键，**未配置**数据库已有的唯一约束（`uk_employees_store_no` 等）、索引与外键。虽然不影响运行（数据库层已有），但：
- EF Core Migrations 会生成与手工 SQL 冲突的建表脚本
- 无法通过 EF Core 检查模型一致性
- 后续维护时容易遗漏约束配置

### 3.3 `ScheduleService.GetMonthViewAsync/GetWeekViewAsync` NPE 风险
**位置**：`ScheduleService.cs` 第 236-251 行、279-297 行
**代码**：
```csharp
var employee = employees.First(e => e.Id == g.Key);  // ← 若员工已被删除则抛异常
```
**问题**：`summaries` 按 `EmployeeId` 分组后，用 `employees.First(e => e.Id == g.Key)` 查找员工。若员工被删除（外键删除被 RESTRICT 阻挡，但员工可能被停用后其排班记录仍在），数据库外键不会允许删除引用中的员工，但**理论上的孤儿数据**会导致 `InvalidOperationException`（未捕获 → 500）。

**修复建议**：改用 `employees.FirstOrDefault(...)` 并在 null 时跳过或用占位名。

### 3.4 `ScheduleService.GetSummaryAsync` 对 `WorkHours.Sum` 的隐式风险
**位置**：`ScheduleService.cs` 第 368 行
```csharp
summaries.Where(x => x.IsRestDay == 0).Sum(x => x.WorkHours)
```
**问题**：`WorkHours` 为 `decimal`，若自动生成排班时某项 `WorkHours` 为负（算法若有 bug），摘要数据可能异常。

### 3.5 员工技能保存无批量校验
**位置**：`EmployeeSkillService.cs` 第 65-108 行
**问题**：`request.Skills` 无上限校验（可提交上千条）、无重复条目预检（仅 `Distinct()` 去重）、`IsPrimarySkill` 无「一个员工只能有一个主技能」的业务校验（多个 `IsPrimarySkill=true` 时算法 `MaxSkillScore` 选择可能受影响）。

### 3.6 换班审批 `sumA`/`sumB` 使用 AsNoTracking 后调用 Remove
**位置**：`Program.cs` 第 1217-1223 行
**代码**：
```csharp
var sumA = await db.ScheduleSummaries.AsNoTracking()...  // AsNoTracking 查询
var sumB = await db.ScheduleSummaries.AsNoTracking()...
if (sumA != null) db.ScheduleSummaries.Remove(sumA);     // 对 Detached 实体调用 Remove
if (sumB != null) db.ScheduleSummaries.Remove(sumB);
```
**问题**：对 `AsNoTracking` 查询的实体调用 `Remove` 虽然 EF Core 会将其 Attach 为 Deleted 处理，但**行为依赖 EF Core 内部实现细节**。若 `sumA`/`sumB` 已被其他查询跟踪，会抛 `InvalidOperationException`。应改为：先查询跟踪实体，或使用 `ExecuteDelete`。

### 3.7 前端 Token 存储在 localStorage
**位置**：`frontend/src/utils/request.js` 第 11 行
```js
const token = localStorage.getItem('shift_token')
```
**问题**：localStorage 可被任意 JS 读取，一旦存在 XSS 漏洞即可窃取 token。且 `localStorage.removeItem('shift_token')` 仅清理 token，**未清理 `shift_role`**，登出后再次进入页面时路由守卫可能读到残留角色。

**修复建议**：改用 httpOnly + Secure + SameSite Cookie；或至少登出时同时清理 `shift_role`。

### 3.8 前端角色仅存 localStorage 可被篡改
**位置**：`frontend/src/router/index.js` 第 133-134 行
```js
const token = localStorage.getItem('shift_token')
const role = localStorage.getItem('shift_role') || ''
```
**问题**：前端路由守卫基于可篡改的 `shift_role` 判断是否进入管理页。虽然后端接口有 `RequireAuthorization`，但**后端未做角色限制**（见 2.1），所以篡改 role 后前端可调用任何管理接口。

### 3.9 管理端分页参数 `(page-1)*pageSize` 潜在溢出
**位置**：`Program.cs` 第 722 行（audit-logs）、`EmployeeService.cs` 第 45 行
```csharp
.Skip((page - 1) * pageSize)
```
**问题**：虽然入口已限制 `page < 1 || pageSize is < 1 or > 100`，但 `page` 可以极大（如 `int.MaxValue`），`(page-1)*pageSize` 会溢出为负数，`Skip` 负数会抛异常（未捕获 → 500）。应限制 `page <= 10000` 或改用 `long`。

### 3.10 `GET /api/schedules/{planId}/week-view` weekStart 无边界校验
**位置**：`Program.cs` 第 464-474 行 + `ScheduleService.GetWeekViewAsync`（254-298 行）
**问题**：`weekStart` 为任意日期时，`start.AddDays(7)` 边界外的数据不返回（合理），但 `weekStart` 若在计划开始前或结束后，无业务提示，前端可能显示空周。

## 四、轻微问题（🟡 建议关注）

### 4.1 参数长度校验缺失
以下请求模型均无 `[MaxLength]` 或后端长度限制：
- `PlanName`（排班计划名）— 无上限，超长会触发 DB 异常或日志膨胀
- `Reason`（请假原因/换班原因）— 无上限
- `Remark`（审批备注/通知备注）— 无上限
- `Phone`（员工电话）— 无格式校验
- `WorkstationUpdateRequest.Status` — 无范围校验（`0/1` 之外可写入）

### 4.2 `AuthService.LoginAsync` 中 `user.StoreId ?? 1`
**位置**：`AuthService.cs` 第 57 行
```csharp
user.StoreId ?? 1
```
**问题**：StoreId 为 null 时硬编码为 1，如果门店 1 被删除或用户未关联门店，审计日志归属错误。应传 `user.StoreId` 本身（可空）。

### 4.3 `DateTime.Now` 未统一使用 UTC
**问题**：全项目使用 `DateTime.Now`（本地时间），若服务器与客户端时区不一致，排班日期与"今天"的判定可能出错。建议统一 `DateTime.UtcNow` 或多地部署时使用 UTC + 存储偏移。

### 4.4 日期解析 `DateOnly.TryParse(month + "-01")` 容错不足
**位置**：`Program.cs` 第 765 行
```csharp
DateOnly.TryParse(month + "-01", out var m)
```
**问题**：`month` 为 `2026-13` 时 `"2026-13-01"` 解析失败，`TryParse` 返回 false 后走默认 30 天逻辑，用户看不到明确错误。

### 4.5 硬编码英文错误码不一致
**问题**：`BusinessException` 的 errorCode 有的用 `INVALID_XXX`，有的用 `XXX_NOT_FOUND`，无统一约定；前端 `res.message` 直接展示（OK），但 errorCode 未在日志中统一处理。

### 4.6 `AllowedHosts: "*"`（生产环境）
**位置**：`appsettings.json` 第 17 行
```json
"AllowedHosts": "*"
```
**问题**：生产环境应限制为具体域名，防止 Host Header 攻击。

## 五、良好实践（✅）

1. **无 SQL 注入风险**：全项目使用 EF Core LINQ 参数化查询，无 `FromSqlRaw`/`ExecuteSqlRaw`/字符串拼接 SQL。
2. **无前端 v-html 使用**：`search_files` 搜索 `v-html` 结果为 0，所有 Vue 模板使用插值自动转义，XSS 主向量被消除。
3. **异常处理完善**：`ApiExceptionMiddleware` 将业务异常/未授权/未找到分类返回，通用异常不泄露内部堆栈。
4. **密码安全存储**：`BcryptPasswordService` 使用 BCrypt work factor 12，Verify 对格式错误哈希安全返回 false。
5. **JWT 配置合理**：SigningKey 长度下限 32 字节、ExpireMinutes 5~1440、OnTokenValidated 检查用户状态（停用即时失效）。
6. **数据库设计质量高**：`init_shift_mvp.sql` 有完整外键、唯一约束（`uk_employees_store_no`、`uk_schedule_summary` 等）、复合索引，字符集统一 utf8mb4。
7. **审计日志覆盖**：登录/增删改/排班/请假/换班均有审计日志记录。
